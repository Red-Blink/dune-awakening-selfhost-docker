# RFC: Automated Discord Command Discovery from Core

**Date:** 2026-08-08
**Status:** Layer 1 Design — Request for Comment
**Audit:** Eight-Hat Layer 1 completed. Findings incorporated.

---

## 1. Problem

The Discord bot and Core console maintain **six independent copies** of the same truth:

| Location | What it tracks | Drift evidence |
|----------|---------------|----------------|
| Core `adapter.js` + `routes.js` | Route paths, handlers, capabilities | — |
| Bot `config.js` `DEFAULT_PATHS`/`METHODS` | Path+method copies (~180 lines) | Must match Core exactly |
| Bot `adapterClient.js` LIVE/PLANNED/UNMERGED/MISSING | Route classification (~130 lines) | 4 documented reconciliations required |
| Bot `commands.js` `buildDuneCommand()` | Discord registration (~150 lines) | Manual per-command |
| Bot `commands.js` `executeDuneCommand()` | Manual dispatch (~350 lines) | Must mirror registration |
| Bot `commands.js` `helpPayload()` + `getCommandRegistry()` | Help text (~200 lines) | Was missing 25 entries until 2026-08-06 |

Every place where data is duplicated is a place where it has **already drifted** and been patched manually. The `adapterClient.js` comment trail ("THIRD reconciliation 2026-08-06", "FOURTH reconciliation 2026-08-08") is the proof that this cannot be maintained by hand.

**The proposal:** Move the source of truth to Core, generate a committed artifact on the bot side, and validate at CI time.

## 2. Architecture

### 2.1 Core Side — Single Source of Truth

**New file:** `console/api/src/integrations/discord/commandCatalog.js`

```javascript
export const DISCORD_COMMAND_CATALOG = {
  version: 1,
  minBotVersion: "1.0.0",
  groups: [
    {
      name: "server",
      description: "Server health, status, and services.",
      subcommands: [
        {
          name: "health",
          description: "Check the console Discord adapter.",
          route: "HEALTH",
          method: "GET",
          tier: "player",
          params: [],
          discordReady: true
        },
        {
          name: "status",
          description: "Show high-level server status.",
          route: "STATUS",
          method: "POST",
          tier: "player",
          params: [
            {
              name: "diagnostic",
              type: "BOOLEAN",
              description: "Admin-only: full diagnostic with containers table.",
              required: false,
              adminOnly: true
            }
          ],
          discordReady: true
        }
      ]
    }
    // ... all groups and subcommands
  ]
};
```

**New endpoint:** `GET /api/integrations/discord/catalog`

Returns the catalog JSON. Bearer-token auth (matching `/health`). Used by:
- Bot's CI generator script (primary consumer)
- Bot's runtime refresh (secondary — validates the committed artifact is current)
- Operator tooling (audit, debugging)

### 2.2 Bot Side — Generated, Committed Artifact

**Generator script:** `scripts/generate-command-registry.js`

```
1. Fetch GET /api/integrations/discord/catalog from Core
2. Merge with bot-side overrides (exclusions, tier adjustments, rename rules)
3. Validate against Core's route classification (no MISSING routes, no UNMERGED routes)
4. Output src/commands-registry.json (committed to repo)
5. If new unclassified routes exist → CI FAILS (requires human review)
```

**Bot-side override file:** `src/commandOverrides.json`

```json
{
  "exclude": ["guild-character-grants-enable", "guild-character-grants-disable"],
  "rename": {
    "ops-inventory": { "subcommand": "armory" }
  },
  "retier": {
    "server-restart": "owner",
    "carepackage-grant-all": "owner"
  }
}
```

**Committed artifact:** `src/commands-registry.json`

Generated by CI, committed to the bot repo. This is the audit trail — an investigator can check out any commit and see exactly what commands were registered at that time.

### 2.3 Runtime — Catalog as Enhancement, Not Dependency

```
Bot startup sequence:
  1. Load commands-registry.json from disk      (instant)
  2. Login to Discord gateway                   (async)
  3. Register commands from committed artifact  (< 2s, before ClientReady)
  4. Mark bot ready
  5. Async: fetch GET /catalog from Core        (background)
  6. Validate: diff committed vs Core catalog   (log mismatches)
  7. If operator runs /dune admin sync-commands → show diff → confirm → re-register
```

**Key properties:**
- Commands are **always available** — the committed artifact provides instant registration before Core is contacted
- Core being unreachable is a **non-blocking background issue** — bot keeps serving the last-known-good catalog
- **Empty/corrupt Core response** does NOT deregister commands — fail-closed for authoritative responses
- **Network blips** are fail-open — keep the cached catalog, retry later
- **`/dune admin sync-commands`** is a manual, operator-triggered sync with confirmation — Core changes never auto-propagate to Discord without review

### 2.4 CI — Drift Detection Gate

`scripts/generate-command-registry.js` runs in CI. If the generated artifact differs from the committed file, **CI fails** — drift is caught before merge.

Additionally, the script validates:
- Every `LIVE_ROUTES` entry has a catalog entry with complete Discord metadata
- No catalog entry references a `MISSING_ROUTES` or `UNMERGED_ROUTES` route
- No catalog entry has an unsupported param type
- No group exceeds Discord's 25-subcommand limit

## 3. Security Model

### 3.1 Bot-Side Allowlist (Architecture B)

Core's catalog provides **metadata for known commands only**. The bot maintains the authoritative list of valid group/subcommand names in `commandOverrides.json`. A command name not in the allowlist is **rejected at registration time** with a logged warning. Core cannot define new command names — this prevents:

- A malicious Core from registering phishing commands
- A compromised Core from injecting fake audit-suppression commands
- A misconfigured Core from accidentally exposing dangerous endpoints (`database:export`, `KillAllPlayers`)

### 3.2 Manual Sync Gate

Core changes to the catalog do NOT auto-propagate to Discord. The operator must run `/dune admin sync-commands` to review the diff and confirm. This provides the human review gate that SOC 2 CC8.1 (change management) requires.

### 3.3 Catalog Endpoint Auth

`GET /api/integrations/discord/catalog` requires the bearer token (matching `/health` auth model). No actor body needed — it's metadata, not a command. The catalog is not secret data (route paths are already public in the bot's open-source code).

### 3.4 Version Binding

The catalog includes `version` and `minBotVersion` fields. The bot refuses to register commands from a catalog with an incompatible protocol version. Core's `/health` endpoint adds `protocolVersion` for future negotiation.

## 4. Migration Path

### Phase 1: Core Catalog (future implementation scope)

1. Core adds `commandCatalog.js` — the single source of truth for Discord command metadata
2. Core adds `GET /api/integrations/discord/catalog` endpoint
3. `DISCORD_LIVE_ADAPTER_ROUTES` becomes derived from the catalog (no separate maintenance)
4. Core's `/health` endpoint adds `protocolVersion` field

### Phase 2: Bot Generator (separate PR)

1. Bot adds `scripts/generate-command-registry.js`
2. Bot adds `src/commandOverrides.json` (exclusions, renames, tier adjustments)
3. Bot adds CI step: regenerate → `git diff --exit-code`
4. Output `src/commands-registry.json` committed as the audit artifact

### Phase 3: Bot Runtime (separate PR)

1. `buildDuneCommand()` loads from `commands-registry.json` instead of hardcoded list
2. `helpPayload()` and `getCommandRegistry()` use the same in-memory registry
3. `adapterClient.js` route classification sets become derived from the catalog
4. `/dune admin sync-commands` command added (diff → confirm → re-register)

### Phase 4: Dynamic Refresh (future)

1. Background catalog refresh with ETags
2. Per-guild catalog cache for multi-tenant deployments
3. Union registration + per-guild dispatch checks
4. Autocomplete handler for item/player/map parameters

## 6. Test Strategy

| Layer | What it tests | File |
|-------|--------------|------|
| L0 — Schema | Catalog JSON validates against schema | `catalogContract.test.js` (Core) |
| L1 — Parser | Bot correctly parses catalog into SlashCommandBuilders | `catalogParser.test.js` (Bot) |
| L2 — Drift | Every LIVE route has complete Discord metadata; no MISSING/UNMERGED routes in catalog | `catalogDrift.test.js` (Bot) |
| L3 — Round-trip | Catalog → registered Discord commands match (HTTP intercept, no real Discord client needed) | `catalogRoundTrip.test.js` (Bot) |
| L4 — Integration | Full flow: fetch catalog → register → fake slash command → correct Core endpoint called | `catalogIntegration.test.js` (Bot) |
| L5 — Boundary | 0 commands, 100+ commands per group, Core unreachable, malformed JSON, version mismatch | `catalogBoundary.test.js` (Bot) |

## 7. Not in Scope

- **Core defining new command names** — the bot's allowlist (`commandOverrides.json`) is the authoritative list of valid commands. Core only provides metadata.
- **Auto-propagation of changes** — changes require operator confirmation via `/dune admin sync-commands`.
- **Per-guild command registration** — deferred to Phase 4 (multi-tenancy).
- **Autocomplete infrastructure** — separate RFC (required for `player:find`, `player:give-item`, etc.).
- **Write commands** — the write adapter bridge (`/write/preview` + `/write/execute`) is a prerequisite, tracked separately.

## 8. Audit Record

**Layer 1 Eight-Hat Findings:**
- Architect: GO with Option A (Runtime Discovery + committed catalog)
- Security: GO with Architecture B (bot-side allowlist) + manual sync gate
- UI/Bot: GO with cached-startup + bot-owned UX (override registry)
- GRC: GO with committed artifact + CI drift gate (not runtime-only auto-discovery)
- DBA: GO — no DB impact (in-memory catalog, static file serving)
- QA: GO with 6-layer test strategy (schema, parser, drift, round-trip, integration, boundary)
- Network: GO with fail-open-for-network, fail-closed-for-corrupt, ETag caching
- CloudSec: GO with bearer-token auth (matching `/health`), no additional secret exposure
