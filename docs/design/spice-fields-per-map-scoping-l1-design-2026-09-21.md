# Spice Fields Per-Map/Per-Partition Scoping — L1 Design

**Date:** 2026-09-21 (Phase 0 discovery completed 2026-09-22, see §4)
**Status:** L1 design. Started **discovery-first** (this document initially proposed zero code changes, just a bounded set of open questions to answer against a live server). **Phase 0 is now complete** (§4 — question 2 answered cleanly positive, questions 1/3 mixed/inconclusive plus a real independent bug found along the way, issue #998), and **§8 now contains Phase 1's actual concrete design** (a frontend-only change, Layer-1-audited a second time specifically, then implemented and reconciled with an unrelated concurrent upstream relocation — see the correction below). Tracked in issue #996.
**Correction (2026-09-22, Phase 2 reconciliation):** upstream's own commit `8eb6715c` ("Improve mobile bases and Spice Field settings", part of release v1.4.37) independently moved this settings section from the `Custom Settings` tab into the `Spice Fields` tab, merging it with that tab's pre-existing read-only "Active Spice Fields" table. Every reference below to "the Custom Settings tab's Spice Fields section" describes where this lived **before** that move -- the settings now render under the `Spice Fields` tab; the Target selector that drives their scope still lives in `Custom Settings` (and `UserGame`), unchanged. This document's own narrative is left as accurate history rather than rewritten line-by-line, per this project's usual convention -- read "Custom Settings" as "Custom Settings originally, now Spice Fields" throughout §1-§9.
**Scope:** whether and how the 9 `SpiceHarvestingSystem` settings (originally `Maps -> Interactive Modifiers -> Custom Settings -> Spice Fields`, added Global-only in PR #228; now `Maps -> Interactive Modifiers -> Spice Fields`, see the correction above) can be extended to real per-map and/or per-partition scoping, matching the existing plain `UserGame` tab's Global -> Map -> Partition precedence model.
**Explicitly out of scope:** Per-field-size or per-field-count control (already established as not possible — see PR #228's own body — this document does not reopen that question).

---

## 1. Problem statement

PR #228 exposed the 9 `SpiceHarvestingSystem` `UserGame.ini` fields (spawn pacing, visibility/replication, yield) at **Global scope only**, deliberately excluding them from the existing per-target `UserGame` tab to avoid a duplicate, unsynchronized editable surface (that PR's Architect-hat finding, MEDIUM, remediated).

A direct follow-up question surfaced the real gap in that decision: **if these were made per-map configurable, what would a Map-scoped override actually change in-game — Deep Desert only? Hagga Basin too? Something else?** The honest answer at the time of asking was "we don't know yet, and we need to find out before building anything" — this document exists to turn that uncertainty into a bounded set of concrete, testable questions, not to paper over it with an assumed answer.

## 2. What's already established (backend capability, verified)

The Global -> Map -> Partition precedence engine in `runtime/scripts/usersettings.py` is generic over every field in `MAP_FIELDS`, with no field-specific special-casing — the 9 spice fields already live in `MAP_FIELDS` exactly like every other per-map-capable setting (`SandStormConfig`, `SecurityZonesSubsystem`, `ResourceLocationSystem`, etc.).

Verified empirically this session: setting Global=5.0, Map(`Survival_1`)=9.0, Partition(`Survival_1`, `3`)=13.0 for `spice_manager_tick_rate_seconds` and compiling via `compiled_usergame_ini()` produced 9.0 for a map-only compile, 13.0 for that specific partition, and 9.0 (correctly inherited from the map) for a sibling partition. `profile_map_values()` / `profile_partition_values()` (`usersettings.py`) do this layering; `write_compiled_usergame()` writes the result to a distinct physical `UserGame.ini` per running map/partition target (`saved_dir_for(map_name, partition_id) / "UserSettings" / "UserGame.ini"`), since each target is its own separate OS process/container (`docs/architecture/SYSTEM-OVERVIEW.md` §1.5) — not a shared process reading multiple maps' config simultaneously.

**Conclusion: the write mechanism is not the open question.** The open question is what the game server actually *does* with a per-instance value for this specific native class, and which of this codebase's map identifiers correspond to which real, player-facing map.

## 3. The map-identifier landscape (more subtle than "HB vs. DD")

Confirmed directly in `runtime/scripts/usersettings.py`, not assumed:

- **`Survival_1`** = Hagga Basin. Persistent world; partitions are individual Sietch instances (`dune-server-survival-1[-<id>]` containers).
- **`DeepDesert_1`** = Deep Desert. A **separate, distinct canonical map identifier** from `Survival_1` — not a partition of some other map (`canonical_map()`, `usersettings.py:1736-1749`). Partitions are dynamically spawned/despawned Deep Desert instances (`dune-server-deepdesert-1-<id>` containers), re-rolled at every weekly Coriolis boundary (`docs/console/live-map.md:171-176`).
- **`Overmap`** = a third, separate always-on coordinator process (`docs/architecture/SYSTEM-OVERVIEW.md` §1.5 lists it alongside `Survival_1` as one of the two "always-on world servers"). **Confirmed by the operator (2026-09-21): Overmap does not host spice fields.** Spice settings only affect `Survival_1` (Hagga Basin) and `DeepDesert_1` (Deep Desert) partitions — Overmap is out of scope for this feature entirely, not a third scoping target to design around.

This means a genuine two-way distinction already exists in the plumbing: a `Survival_1`-scoped override is a different write than a `DeepDesert_1`-scoped override, targeting physically different containers' `UserGame.ini` files. That part is a fact, not a guess. **`Overmap` is confirmed inert for spice and should be excluded from any future Target selector for this feature** — exposing an Overmap-scoped Spice Fields control would be actively misleading, per §4/§6's own reasoning about a control that does nothing. What remains unconfirmed is what a `Survival_1`- or `DeepDesert_1`-scoped override actually *does* to the running game.

**Note on evidentiary standard (Architect-hat finding, §7):** this document holds every other claim to a "concrete, falsifiable test" standard (§4) but the Overmap exclusion rests on a direct, first-hand operator statement about the live system rather than a document-internal test — trusted as ground truth (the operator runs and observes these servers directly), but Phase 0 should still include one cheap, non-blocking sanity check (e.g. confirm no spice-related log lines or state ever appear for the Overmap container) so this exclusion is corroborated the same way as everything else, not just asserted.

## 4. Open questions — must be answered on dune-dev before any design proceeds

Each of these is a concrete, falsifiable test, not a rhetorical question. (Overmap is excluded from this list — confirmed inert for spice, see §3 and its sanity-check note.)

**Precondition:** before running any of these, confirm dune-dev currently has both a `Survival_1` and a `DeepDesert_1` partition provisioned and running (Architect-hat finding, §7) — not assumed from this document alone.

1. ~~Does a `Survival_1`-scoped spice override change Hagga Basin's spice behavior without affecting Deep Desert, and vice versa?~~ **PARTIALLY ANSWERED (2026-09-21, see issue #996): mixed.** **Config-write isolation is cleanly confirmed** — Survival_1's compiled `UserGame.ini` only ever showed its own override, never Deep Desert's or Overmap's, across every test run. **Behavioral isolation is plausible but not cleanly proven.** Log-grepping (`LogSpiceField`/`LogResourceField`) produced no periodic, tick-correlated signal — pivoted to querying `dune.resourcefield_state` (Postgres) for real spawn timestamps, which worked but revealed spawning is bursty/event-driven, not a steady rate (one 10-min default-config window: 0 new spawns; another: 18) — short windows are unreliable for this comparison. **A real, independent bug was found as a byproduct and filed separately (issue #998):** `spice_spawning_active=False` does not fully stop new spawns (confirmed nonzero across two windows, 18/10min and 3/45min) — this confounds interpreting "did the map override work" vs. "does this specific field work at all," and its description was corrected (PR #999) but its root cause remains unresolved. **Recommendation for Phase 1:** treat behavioral map-isolation as likely-true but not rigorously proven; re-test with a field known to behave correctly (not `spice_spawning_active`) if a stronger guarantee is needed before shipping, rather than blocking Phase 1 entirely on it.
2. ~~Does a Deep Desert Partition-scoped override survive a Coriolis re-roll...~~ **ANSWERED (2026-09-22, see issue #996): yes.** Set a Partition-scoped `spice_prime_rate_seconds=111` override on live partition `8`, waited for the real Coriolis boundary (2026-09-22 11:00 UTC, confirmed via the server's own logs: seed changed 6→7, cycle-start timestamp advanced). The partition ID was unchanged (still `8`), but the container demonstrably restarted right at the boundary (uptime reset, matching the 04:00 PDT/11:00 UTC window) — so a boundary *does* cause a real respawn, not a silent in-place reseed, at least in this observation. The override survived: present in the profile, present in the currently-running process's own freshly-regenerated compiled `UserGame.ini` (confirmed via file mtime), Global default untouched. **Residual, non-blocking unknown:** this only covers the case where the partition ID survives the boundary — whether a genuinely *new* partition ID would carry the override forward is untested (lower priority; Map-scoped remains the safe fallback either way). Phase 1 can offer Partition-level scoping for Deep Desert without the "does it silently evaporate weekly" caveat that was blocking it.
3. **Does the real Funcom `SpiceHarvestingSystem` C++ class actually read `UserGame.ini` per-instance, or does it cache/share state in some way this codebase can't see from the outside?** No source access exists for this class (closed-source game server) — this question has no independent test of its own; it was meant to be answered by question 1's result (QA-hat finding, §7). Since question 1 came back mixed rather than a clean pass, this question is **also inconclusive by extension**, not confirmed either way. Question 2's positive result (a Partition-scoped override did survive a restart and land correctly in the right process's own compiled file) is at least consistent with per-instance reads working correctly for the field tested there (`spice_prime_rate_seconds`) — but doesn't generalize to all 9 fields given `spice_spawning_active`'s demonstrated anomaly (#998).

**Phase 0 status: complete as of 2026-09-22.** Question 2 has a clean, positive, evidence-backed answer. Questions 1 and 3 have real evidence but a mixed, non-definitive answer, plus a genuine independent bug found along the way (#998). This is enough to proceed to Phase 1 — config-write isolation (the structural question Phase 1's UI depends on) is solid; the remaining behavioral uncertainty is a reason for Phase 1 to be conservative about claims made to operators, not a reason to keep blocking on more live-server time.

## 5. Proposed phased approach

**Phase 0 — Discovery (this issue, no code changes):** run the three tests in §4 (plus the Overmap sanity check in §3) against dune-dev (per this project's own convention of using dune-dev for exactly this kind of live experiment). Any test value set during discovery can be cleared the same way as any other `MAP_FIELDS` override (`profile_remove_key`, generic — no spice-specific recovery path exists or is needed; confirmed directly against `usersettings.py`, DBA-hat finding, §7) — there is no bespoke rollback procedure to design or worry about for this phase. Record results, with real log/screenshot evidence, as a comment on issue #996 (Requirement 20's evidence-trail discipline applies even at the discovery stage, not just to audits of finished code).

**Phase 1 — Design revision, gated on Phase 0:** once the real behavior is known, revise this document (or file a new L1 design) with an actual proposed UI/backend shape:
- The Target selector for this feature should offer `Survival_1` and `DeepDesert_1` only (Overmap excluded, confirmed inert) — but its absence must be communicated to the operator, not just silently omitted (UI/UX-hat finding, §7). The plain `UserGame` tab's own Target selector already lists Overmap as a normal, selectable target for every other setting; an operator familiar with that dropdown would reasonably expect the same list here. Phase 1 must decide how to surface the reason (e.g. a disabled/greyed Overmap option with a tooltip explaining it doesn't apply to spice, rather than a silent gap that reads as a bug).
- Partition-level scoping should only be offered for whichever of §4's questions confirm it's meaningful (a Deep Desert Partition control that silently resets every Coriolis boundary should not ship as if it persists).
- This phase must also solve the duplicate-editable-surface problem PR #228's Global-only design sidestepped, **without silently reversing PR #228's own discoverability fix.** PR #228 moved Spice Fields out of the generic UserGame tab's buried Modifier-Category dropdown specifically because it "was not anywhere near where an operator... would think to look" — folding it back into that same dropdown to solve the duplicate-surface problem would re-introduce the exact discoverability regression PR #228 fixed, not a neutral tradeoff (UI/UX-hat finding, §7). Phase 1 must explicitly evaluate this tradeoff (e.g. keep Spice Fields as its own dedicated, visible section but drive its Target selector off the same shared state the per-target settings already use, so there's one source of truth even though there are still two visual entry points) rather than defaulting to the fold-back option.

**Phase 2 — Implementation, gated on Phase 1:** normal Eight Hats Layer 2 (implementation) and Layer 3 (integration) audits, upstream PR draft-mode gating (Requirement 19), same process as PR #228.

## 6. Why this isn't being fast-tracked

The honest, stated reason to pause here rather than build immediately: extending scope to Map/Partition without confirming §4 risks either (a) a control that does nothing (already caught once for `Overmap`, per §3 — confirming the risk is real, not hypothetical), which is worse than no control because it implies a capability that doesn't exist, or (b) a control whose effect silently evaporates on Deep Desert's own weekly reset cycle, which would be actively misleading to an operator who set a Partition-scoped value expecting it to stick. Both are exactly the class of harm Strict Requirement 0 ("a fix must not be riskier than the problem it fixes... could this desynchronize from something outside this codebase that I can't see or test against from here?") exists to catch before shipping, not after an operator reports it confusing.

## 8. Phase 1 — concrete design (2026-09-22)

Phase 0 is complete (§4). This section is the actual UI/backend shape, gated on those results.

### 8.1 Core decision: reuse the existing shared Target selector, don't build a second one

The `Custom Settings` tab already has a fully working Target selector — `userGameName` / `effectiveUserGamePartitionId` / `isUserGameGlobal` state, populated by `buildUserGameTargets(mapRows, serverPartitionRows, survivalSietchRows, deepDesertPartitionRows)` (`MapsPanel.tsx:2983-2998`), with `Survival_1`, its Sietch partitions, `DeepDesert_1`, its partitions, `Overmap`, and `"__global__"` all already real, selectable options. The existing per-target `UserGame`/`Custom Settings` save logic (`MapsPanel.tsx:1881-1893`) derives `scope`/`map`/`partitionId` from exactly these three variables.

**Decision: the Spice Fields section reacts to this same, already-selected target — it does not get its own, separate Target dropdown.** This was the L1 audit's UI/UX-hat suggestion in §5 ("drive its Target selector off the same shared state") taken to its natural conclusion: don't build a second selector that merely *reads from* shared state, reuse the one selector directly. A second dropdown would be more UI, more state to keep synchronized, and reintroduces exactly the kind of two-controls-for-one-concept risk the original duplicate-surface finding was about — just moved from "two edit surfaces" to "two selectors for one edit surface." Rejected as unnecessary complexity — Global scope, and every Map/Partition target, are already correctly enumerated by the existing mechanism; there is nothing left for a second selector to do that the first one doesn't already do.

### 8.2 Preserving "visible without selecting a Target" for the common case

PR #228's Spice Fields section is explicitly tested (`docs/console/spice-fields-custom-settings-uat.md` §1) to be visible and populated *without* any Target selected — this was a deliberate design point (most operators only ever want Global spice tuning). Making the section fully Target-driven would break that: with no target chosen, `userGameName` is empty, and the section would go empty/prompting exactly like the rest of Custom Settings does today.

**Decision: when no Target is selected (`!userGameName`), the section defaults to Global scope** — behaviorally identical to today's PR #228 UX. When a Target *is* selected (`Survival_1`, a Sietch partition, `DeepDesert_1`, a Deep Desert partition, `Overmap`, or explicit `"__global__"`), the section reads/writes that target's own scope, exactly like the rest of the tab. This is a strict superset of current behavior — nothing an existing operator does today changes; the only new capability is that selecting a Target now also affects Spice Fields, which it doesn't today.

**Required: a persistent, always-visible scope indicator in the Spice Fields section itself (UI/UX-hat finding, §9), not prose alone.** Before this change, Spice Fields was immune to the page-level Target selector; after, that selector silently changes what a section further down the page is editing — real action-at-a-distance risk (an operator scrolls to Spice Fields out of habit expecting Global, or forgets they reselected a Target earlier). A rewritten explanatory paragraph (§8.6) is not sufficient on its own. Add a small, always-visible label directly in the section's own header, e.g. "Editing: Global" / "Editing: Hagga Basin — Sietch 3" / "Editing: Deep Desert — Partition 8", driven by the same state already available (§8.1) — cheap to add, and it closes this gap structurally rather than relying on an operator having read the paragraph.

**Known, pre-existing, inherited risk — not new to this design (QA-hat finding, §9):** switching the Target selector while the Spice Fields grid has unsaved draft edits will silently discard them, exactly like every other field in the `Custom Settings`/`UserGame` tab already does today — confirmed directly: `loadSelectedSettings()` (`MapsPanel.tsx:842-846`) unconditionally overwrites `gameDraft` with the newly-loaded target's server values, and none of the target-switch handlers (`selectMap`/`selectDeepDesertPartition`/`selectSietch`/`selectPartition`, `MapsPanel.tsx:1420-1487`) check for a dirty draft or confirm before switching. Extending Spice Fields to follow the same selector means it inherits this same behavior for the first time (today it's immune, since it ignores the selector). This is a real, already-accepted UX gap across the whole tab, not something Phase 1 introduces — fixing it properly (a "discard unsaved changes?" confirmation on target switch) would benefit every field, not just spice, and is explicitly out of scope for this design. Phase 1 should not invent a spice-specific fix that diverges from the rest of the tab's existing behavior; if this gap is worth closing, it should be a separate, tab-wide follow-up, not bundled into this feature.

### 8.3 Overmap handling — explained, not hidden

The shared Target dropdown is used by other settings too and already lists Overmap as a normal, real option (confirmed live — every other `MAP_FIELDS`-backed section, e.g. the plain `UserGame` category grid, works fine with Overmap selected). Removing Overmap from the shared dropdown to protect Spice Fields specifically isn't viable without breaking every other section that legitimately needs it.

**Decision:** when Overmap is the active target, the Spice Fields section shows an explicit, worded empty state ("Spice Fields don't apply to Overmap — Overmap doesn't host spice fields; select Global, Hagga Basin, or Deep Desert instead") in place of the field grid, using the same `emptyMessage` mechanism `SettingsCardGrid` already takes (`MapsPanel.tsx:2416`, `modifierEmptyMessage(...)`) — just with Overmap-specific copy rather than the generic "select a Target" message. This directly answers the UI/UX-hat's §7 finding (Overmap's absence needs to be communicated, not silent) without touching the shared dropdown at all. **This empty state should be visually distinct from the ordinary "select a Target" placeholder** (UI/UX-hat finding, §9) — reusing the exact same styling risks a fast-skimming operator misreading a deliberate exclusion as the generic "you haven't picked anything yet" state. A small icon or distinct visual treatment is enough; not blocking Phase 2, but should be done in the same pass.

### 8.4 Partition-level scoping — offer for both Survival_1 and Deep Desert

Test 2 (§4) confirmed a Deep Desert Partition-scoped override survives a Coriolis re-roll when the partition ID is preserved. Survival_1's Sietch-partition scoping is already a proven, working pattern for every other `MAP_FIELDS` entry via the exact same code path. **Decision: offer Partition-level scoping for Spice Fields on both maps**, with no special-casing needed — the existing `userGameTargets` list already includes both maps' partitions; nothing new to build here beyond making Spice Fields honor whatever target is selected (§8.1).

**Concrete acceptance test (QA-hat finding, §9):** "no special-casing needed" is a claim, not yet a check — Phase 2's test suite should explicitly set a Sietch-partition spice override and a Deep-Desert-partition spice override independently (in the same run, different fields or different partitions to avoid confounding, per the Phase 0 methodology in §4), and verify each lands only in its own compiled `UserGame.ini`, not the other's and not Global's.

### 8.5 Backend: no changes needed

Confirmed independently twice this session (the initial capability investigation and the DBA hat's Layer 1 review, §7): `profile_map_values()`, `profile_partition_values()`, `compiled_usergame_ini()`, `profile_set_key()`/`profile_remove_key()` are all fully generic over every `MAP_FIELDS` entry, spice included. **This is a frontend-only change** — no Python schema change, no new API route, no migration.

**Scope of what's actually been behaviorally validated (QA-hat finding, §9):** the genericity claim above is code-verified (structural), not behaviorally exercised for all 9 fields — Phase 0 only behaviorally tested 2 of the 9 (`spice_manager_tick_rate_seconds`, `spice_prime_rate_seconds`), plus one known-broken field (`spice_spawning_active`, #998). Phase 2's test plan must not treat "no backend changes needed" as fully validated for all 9 fields just because it's structurally true — it should exercise a broader sample of the 9 (ideally all of them) through the new Target-aware path before that claim is considered end-to-end validated, not just structurally sound.

### 8.6 Concrete frontend changes

- `loadSpiceFieldSettings()` (`MapsPanel.tsx:870-876`): currently hardcodes `mapsApi.userGame("__global__")`. Change to derive its target from `userGameName`/`effectiveUserGamePartitionId`/`isUserGameGlobal` per §8.2 (default to `"__global__"` when `userGameName` is empty), mirroring exactly how the existing per-target load already works for the rest of the tab.
- `saveSpiceFields()` (`MapsPanel.tsx:1912-1921`): currently hardcodes `{ scope: "global", map: "Survival_1", ... }`. Change to derive `scope`/`map`/`partitionId` the same way `saveGame()`'s derivation logic does at `MapsPanel.tsx:1882-1884` specifically — **not** line 1881 (`if (!userGameName) return;`), which is `saveGame()`'s own early-return guard for "nothing selected." Copying that guard verbatim would silently break §8.2's explicit promise that Spice Fields must still save at Global scope when no Target is selected — `saveSpiceFields()` needs the derivation logic only, with its own separate default-to-Global fallback in place of that guard (Architect-hat finding, §9).
- `SettingsCardGrid`'s `emptyMessage` for the Spice Fields grid (`MapsPanel.tsx:2416`): add the Overmap-specific case from §8.3.
- The section's explanatory paragraph (currently states these settings "apply server-wide, independent of the Target selector above") needs rewriting — that claim becomes false the moment Target-awareness ships. New copy should state plainly: with no Target selected, these apply server-wide (Global); with a Target selected, they apply to that map/partition specifically, same as every other Custom Settings field.
- **What does not change:** the generic `UserGame` tab's permanent exclusion of category `"Spice Fields"` (`MapsPanel.tsx:1361`) — Spice Fields stays out of that tab forever, preserving the single-editable-surface property from PR #228. Action row labels, Discard/Restore Defaults mechanics, the filter input, and the save-restart-confirmation flow are all already target-scope-agnostic and need no change.

### 8.7 Operator-facing caution, carried forward from Test 1's mixed result

Test 1 (§4) showed config-write isolation is solid but full behavioral isolation isn't rigorously proven, and surfaced a real, independent bug (`spice_spawning_active`, issue #998) where a field's actual behavior doesn't match its description. **Decision: no new UI copy in this feature should imply a stronger behavioral guarantee than what's actually confirmed** — rely on each field's own (already-corrected where needed, e.g. PR #999) description rather than adding a blanket "map-scoped changes are fully isolated" claim to the section's own explanatory text. The PR body and UAT doc for this feature should state plainly that per-map write isolation is confirmed but full behavioral isolation per-field is not guaranteed, linking #998 as a known, separate, open issue.

**Concrete Phase 2 checklist for this guardrail (QA-hat finding, §9)**, since "don't overclaim" is a principle an implementer can't mechanically verify compliance with on their own:
1. Ban absolute terms ("guaranteed," "fully isolated," "verified for all fields") in any new or changed UI copy, unless the claim is directly tied to a cited Phase 0/2 test result.
2. Any behavioral claim in new copy must reference the specific test it rests on (e.g. "confirmed via issue #996" rather than a bare assertion).
3. Whoever reviews the Phase 2 PR explicitly checks every new/changed copy string against items 1-2 before merge — call this out in the PR body's own documentation-review section (Requirement 14).

### 8.8 Rejected alternative

A separate, dedicated Target selector just for Spice Fields (rather than reusing the shared one) was considered — this was the literal wording of the L1 audit's Phase 1 guidance in §5. Rejected per §8.1: it adds a second piece of state that must be kept in sync with the first for no behavioral benefit, since the shared selector already enumerates every target Spice Fields needs (Global, both maps, both maps' partitions, Overmap). Re-using it is strictly simpler and structurally impossible to desynchronize, since there's only one selector to begin with.
